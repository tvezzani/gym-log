# API and persistence rules

Milestone 2 decisions, October 21, 2026. `openapi.yaml` is generated by `npm run docs:generate` from the browser-safe Zod contracts. `npm run docs:check` validates it and detects schema drift. Authentication, account administration and own preferences are implemented. Exercise/set/plan rules describe milestone 4 handlers; migrations alone do not enforce API authorization or concurrency workflows.

## Ownership and exercise lifecycle

Every set/plan lookup and mutation includes the session's `user_id`, even for admin. Never accept `userId` in a request body/query. Return 404 for an unknown or inaccessible private resource. Admin account/catalog permissions do not grant access to other people's sets, plans, or their last values. Database operator access is separate. The shared backend database role is not an end-user security boundary; there is no claim of row-level isolation from SQL alone.

The exercise picker combines approved/unarchived catalog entries with the caller's own unarchived pending submissions. Another user's pending or rejected ID is unavailable even if guessed. Rejection and archive block new selection for both sets and plans. Existing sets/plans keep their exercise ID and remain readable/editable; retaining that same ID is allowed, but selecting a different ID requires current eligibility. Logging from an unavailable planned exercise is blocked. Only admin can rename, archive/unarchive, approve, or reject. There are no user-specific aliases or local rename variants. Rejection has no reason field in v1.

Names need not be unique. Approval keeps the ID stable and shares only the exercise with authenticated family accounts, never on the internet. Renaming changes the display name for references to that exercise, including history; old name spellings are not snapshotted. Embedded exercise references let owned historical rows display rejected/archived status without allowing selection. Users can read their own submission statuses; admins can read the review queue. Review is a pending-to-approved/rejected transition, with server reviewer/time metadata.

For a new selection, use `SELECT ... FOR SHARE` on the selected exercise within the write transaction, recheck eligibility, and retain the lock through commit. Review, rename and archive acquire `FOR UPDATE` on that row. An existing-reference edit locks/checks the owned set/plan as well. This prevents archive/review races from bypassing eligibility. Handle deadlocks by rolling back/retrying the whole transaction with bounded retries; never continue a failed transaction.

## Validation, numbers and time

All defined request-body and query schemas are strict: unknown fields fail validation, and empty PATCH objects fail. Semantic validation returns 422 with `error.code=VALIDATION_ERROR` and optional `fieldErrors` (path/message only). Malformed JSON returns 400, oversized bodies 413, unsupported encoding 415, expired/disabled/revoked authentication 401, role/CSRF denial 403, inaccessible resources 404, and state conflicts 409. Error responses never include raw input, SQL, stack traces, hashes, or credentials. JSON bodies are limited to 32 KiB.

Weight is a JSON decimal string from `0` to `99999.999` pounds, with at most three fractional places and no sign, exponent, whitespace or leading zeroes. Reject overprecision before passing the value to SQL: `numeric(8,3)` otherwise rounds it before a CHECK can inspect it. Return normalized decimal strings (for example `135.500` becomes `135.5`). Never convert weight through a JavaScript floating-point number. `pg` returns numeric columns as strings; keep weight as text and explicitly convert bounded integral fields to JSON numbers.

Reps and set numbers are integral values from 1 to 2147483647; RPE is an integer from 1 to 10, default 5. Fresh set number defaults to 1. SQL stores these using `numeric` plus range/integrality checks: this rejects numeric literals such as `5.5` rather than allowing an integer-column assignment to round them. Set numbers are never unique per exercise/day. UUIDs are canonicalized to lowercase when normalizing retry requests.

`performedAt` is required on create so retries cannot generate a different time. Require an ISO 8601 instant with `Z` or a numeric offset and exactly three fractional digits; reject finer precision. Normalize to UTC on responses. Store `timestamptz(3)`. `createdAt`/`updatedAt` are server metadata, with an update trigger. Dates/instants must be finite. Workout-day queries use a start-inclusive/end-exclusive interval for the stored IANA timezone; a day may span 23 or 25 hours at DST changes. Latest values use the same owner/exercise-filtered history list with `limit=1` and no time bounds.

`plannedDate` is a real calendar date, years 0001–9999, represented as `YYYY-MM-DD` and SQL `date`. Select it as `planned_date::text`; the default pg date parser must not turn it into a JavaScript date. Notes are plain text up to 2000 characters and are not parsed into sets. User timezone is supplied when creating the account, validated against IANA names (and PostgreSQL's supported names), stored explicitly and changed through `PATCH /preferences`. Traveling does not change it, and a timezone change never moves a plan date.

## Stable create retries

`canonicalWorkoutCreate` validates and serializes a fixed field order. It normalizes UUID case, performed instants to UTC, decimal trailing zeros, and omitted defaults (`setNumber=1`, `rpe=5`). Hash the resulting UTF-8 text with SHA-256 on the server. The owner is taken from the session and stored separately. No server-generated performed time participates in retry handling.

In one transaction, attempt an insert into `workout_create_requests` using the client UUID, session owner and hash (`ON CONFLICT(id) DO NOTHING`). A competing insert waits for the first transaction's commit/rollback. For an existing identity, compare both owner and original hash; conflicting requests return a generic 409 with no other account data. For a matching retry, read/lock the owned set and return 200 with its current values. Do this before applying current exercise-eligibility rules: a replay is not a new selection. If the set has since been edited, do not overwrite those edits. If deleted, return 410; never recreate it.

For a genuinely new identity, validate/lock the exercise and write the set before committing. An invalid exercise or failed write rolls back the new ledger row too. Both identity and set creation must commit together. The set has a composite foreign key to its ledger's ID/owner. The runtime role cannot update/delete ledger entries. DELETE removes the actual set; retain only UUID, owner, original request hash and creation time in the ledger, preventing resurrection without retaining deleted set values. The original hash is unchanged by edits. This ledger is durable v1 retry bookkeeping and is not pruned on session expiry.

## Pagination and plan ordering

List requests accept `limit=1..100` (default 50), `offset=0..100000` (default 0), with `{items,pagination:{limit,offset,hasMore}}` responses. Fetch one extra row to determine `hasMore`. Sort ties always use ID. Offset paging has no snapshot guarantee while other requests insert/delete; clients reload the current view after mutations.

| List             | Ordering                     |
| ---------------- | ---------------------------- |
| Workouts         | `performed_at DESC, id DESC` |
| Shared exercises | `lower(name) ASC, id ASC`    |
| Own submissions  | `created_at DESC, id DESC`   |
| Review queue     | `created_at ASC, id ASC`     |
| Accounts         | `username ASC, id ASC`       |
| One date's plans | `sort_order ASC, id ASC`     |

All plan create/delete/move/reorder operations acquire the same transaction advisory lock derived from the authenticated owner and calendar date. Moving dates locks both keys in deterministic order. Append new/moved entries after the existing last position, with at most 500 entries per owner/date. The bound is an API transaction rule, not a SQL CHECK across rows.

`PUT /planned-exercises/order` supplies every ID currently on that owned date exactly once. Under the common lock, compare the full membership, defer `app.plans_owner_date_order`, update all positions to 0..n-1, and commit. Foreign IDs, omitted IDs, duplicates, or stale membership fail without partial updates. Existing gaps after deletion do not matter. Reorder never changes exercise references or generates workouts. Logging from a plan is a later UI prefill action only.

## Accounts and sessions

Usernames are canonical lowercase ASCII `[a-z0-9_]{3,32}`, unique in PostgreSQL. API username fields require that form; the UI may lowercase user input before submission. New/reset passwords are 12–128 characters and are never trimmed/normalized. Current/login passwords allow 1–128 to validate existing credentials. Store a maintained Argon2id hash, never raw passwords. The SQL hash-shape check is not a substitute for Argon2 verification.

Opaque sessions store only a SHA-256 session-token hash, user ID, CSRF token, creation time, expiry and optional revocation time. The CSRF token is separate from the session secret and may be returned to the same-origin caller. Session cookies are HttpOnly/SameSite=Lax, Secure on production HTTPS, with a documented loopback-HTTP development exception. GET `/auth/csrf` establishes signed pre-login CSRF context; login validates CSRF/origin and replaces the session. Auth responses are not cacheable. No raw session token or hash is returned in JSON.

Account disable and password reset revoke sessions transactionally; an own-password change revokes all own sessions including the current one. Recheck active user and live/unexpired session on every authenticated request. Use one common transaction lock for admin role/disable changes so concurrent requests cannot remove the last active admin. There is no destructive account deletion in v1; foreign keys preserve references. Expired session rows may be removed after `expires_at`; revoked rows remain unusable and may be retained until expiry. Durable workout retry identities are unrelated to sessions.

Sessions now expire after exactly 30 × 24 hours without sliding renewal. New/bootstrap/reset accounts have `mustChangePassword=true`; until a different password is set they may only obtain CSRF, read own auth state, change password, or sign out. A password change clears the flag and revokes all own sessions. Role changes also revoke the target’s sessions. Exactly two roles exist: user and admin, in one family instance without tenancy. The bootstrap/retention/rate-limit configuration and verified auth transaction rules are documented in `AUTH.md`. All mutations require the exact configured `Origin` as well as CSRF.

## Persistence and recovery

The schema uses parameterized SQL through `pg`, SQL-file migrations through node-pg-migrate, explicit foreign keys, checks and indexes. There is no ORM or query builder. Application ownership, exercise eligibility, last-admin protection and retry/reorder transactions still require the forthcoming handlers and API integration tests; the schema does not replace them.

Run migrations explicitly with the operator URL; runtime API traffic uses `gym_app`. A migration failure rolls back transactionally; fix the cause and rerun. Do not modify applied files. The domain migration refuses a destructive down operation. For production changes, take and verify a backup and document compatible app/schema versions; restore a verified backup or apply a reviewed forward recovery migration. Rolling back an application build does not undo SQL. Development fixture and isolated database-test commands are documented in `db/README.md`.
